项目背景：跨境卖家的真实痛点

业务痛点

一个 Listing 上线需要：查平台政策 → 查关税税率 → 算利润 → 写文案 → 做素材图 → 拍视频

每步都要打开不同工具网站，来回切换，效率极低

小团队没有专职运营，老板自己要查 4-5 个系统才能做出一个选品决策

技术痛点

通用 AI 只能聊天，不知道关税、汇率、物流等实时数据

AI 容易"幻觉"——编造不存在的政策条款和数据

选品需要亚马逊真实竞品数据，但市面上 API 要么翻墙、要么贵

解决思路

构建一个 AI Agent：用户用自然语言下达任务，Agent 自主调度工具链完成全链路运营操作。
关键技术挑战：Function Call 工具编排、幻觉治理、多数据源容灾、多模态内容生成。

Agent 调度核心：ReAct + Function Call

基于 LangChain 0.2 的 create_agent（底层 langgraph），13 个工具统一注册为 Function Call 签名

STEP 1 · 用户输入
"把玻璃杯出口到美国，货值500美元，分析选品并算利润"
STEP 2 · Agent 推理（ReAct）
模型分析意图→需要选品数据→需要关税税率→需要利润计算→串行调用3个工具
STEP 3 · Function Call 执行
selection_by_image(image_path, 玻璃杯) → query_tariff(美国, 玻璃制品, 500) → calc_profit(售价, 成本, 关税)
STEP 4 · 幻觉治理
收集知识库上下文 + 所有工具返回 → 6步校验 → 低质量回答自动追加风险提示 → 最终答案
关键设计：tool_call_id 精确匹配机制——解决连续调用同名工具（如两次汇率换算）时结果错位问题

工具详解：智能选品分析

项目最复杂的工具，覆盖从数据采集到商业研判的全链路

1. 竞品数据采集
三数据源自适应路由：Proboost MCP（国内直连）→ Canopy API（100次/月免费）→ Rainforest API（100次/月免费），四级降级链（缓存→MySQL→在线API→内置基线）
fetch_rainforest_competitors("玻璃杯", "美国") → 按英文搜索词查 amazon.com → 解析标题/价格/评分/评论数/ASIN/商品图
2. 成本利润核算
对每个竞品套用自有成本模板：售价 − 采购成本 − 头程运费 − 平台佣金(15%) − 广告费率(10%) − 退货损耗 = 净利润。算完自动标记利润率合格/不合格
批量利润核算 → 筛品过滤器（蓝海/中度/红海三级分级）
3. 评论痛点拆解
低评分竞品(≤4.2)→调用 Rainforest reviews API 拉真实评论文本→评分×评论数×价格三维交叉推断痛点类型→匹配改款方案→输出差异化卖点建议
fetch_rainforest_reviews(asin) → 分析低评分竞品 → 推断痛点类型 → 7种改进方案映射

工具详解：关税查询 & Listing生成

关税查询（query_tariff）
数据来源：基于 USITC HTS 2025、EU TARIC 2025、Japan Customs Tariff Schedule 官方税率手工整理
支持品类：电子产品/服装/家居用品/玻璃制品/美妆/宠物用品/玩具/鞋类/灯具
计算逻辑：应缴关税 = (货值+运费)×税率，低于免税额度时自动显示免征
HS编码覆盖：玻璃制品 7013.37、电子产品 8517.62、家居用品 3924.10 等
费率：美国最惠国 0%-25%、欧盟0%-17%、日本0%-10%
Listing生成（generate_listing）
精品/铺货双模式：精品模式含品牌故事+A+内容，铺货模式快速批量
SEO 关键词分层：核心词→长尾词→场景词三级，配合五点描述+产品描述
合规双检：违禁词过滤 + 极限词过滤，"第一""最好"等自动标记风险
痛点差异化：从痛点分析结果提取竞品弱点，写入 Listing 作为差异化卖点
多语言：支持英文/中文/日文输出

核心技术：三数据源自适应路由

解决海外 API 无法直接访问的痛点，自动检测可用数据源并路由

数据源类型接入方式免费额度国内访问路由优先级
Proboost MCP阿里云市场 MCPSSE + JSON-RPC + 转义JSON解析按量计费直连1st
Canopy API海外 REST+GraphQLAPI-KEY Header100次/月需代理2nd
Rainforest API海外 RESTapi_key Query100次/月需代理3rd

路由逻辑

if PROBOOST_MCP_TOKEN: route to proboost
elif CANOPY_API_KEY: route to canopy
else: route to rainforest

Proboost 接入难点：MCP 返回格式是 markdown 说明表+内嵌转义JSON，需特殊解析（花括号栈匹配+JSON unescape）

核心技术：六步幻觉治理

项目最大技术难点——不是简单过滤，而是与 Function Call 协同工作

六步校验流程

1. 未命中检测：KB 上下文是否覆盖答案领域

2. 关键词覆盖：答案关键词在上下文中出现率

3. 绝对化惩罚："一定""绝对""所有"等词降权

4. 长度检查：超出知识支撑范围的发散内容

5. 数字核查：关税/汇率数字是否来自工具

6. 归一化评分：0~1 置信度，低于阈值追加警告

关键 Bug 修复：双上下文

问题：Agent 正确调用 query_tariff + convert_currency，回答"关税 25%，约 899 元"，被误判幻觉

根因：只收集 search_kb 返回做校验上下文，工具返回的数字在 KB 中找不到

修复：新增 _collect_tool_context，综合上下文 = KB + 全部工具返回，工具返回的数字也算有效支撑

核心技术：混合检索 RAG

知识库架构

文档上传 → 500字切片(80字重叠) → BGE-small-zh-v1.5 向量化 → Chroma 存储

4个集合：产品参数库、平台规则库、爆款文案库、风险案例库

混合检索策略

问题：纯向量检索对专有名词（如"HS编码""FBA"）命中率低

方案：向量检索(余弦相似度) + jieba关键词重叠率重排

加权融合：final_score = 0.7×vec_score + 0.3×kw_score

阈值 0.35 过滤，低于则标记"知识库未命中"

多模型路由（附加创新）

简单问题（翻译、格式转换）→ DeepSeek-fast（省成本）；复杂推理（选品分析、文案生成）→ DeepSeek-pro。自动根据 query 长度和关键词判断路由

工程难点与踩坑记录

#1 幻觉治理与 Function Call 协同（最难）
Agent 基于工具结果正确回答被判幻觉→修复为双上下文校验（KB+工具返回）
#2 连续 tool_call 结果错位
两次 convert_currency 结果交叉错位→改用 tool_call_id 精确匹配而非顺序索引
#3 DeepSeek 不支持中文 Function Name
Invalid function name pattern → @tool("english_name")显式注册，Python函数名保留中文
#4 Pydantic v2 类型校验
session_id: str = Field(None) 不规范，偶发 422 → 改为 str | None = Field(None)
#5 记忆模块会话删除 Bug
add_message 降级逻辑生成双份 key → _mem_sessions 残留导致删不掉 → 直接构造 session 字典
#6 DashScope 模型迭代适配
wanx2.1-t2i-turbo 下线→升级 wan2.7-image；happyhorse 视频黑屏→切换 wan2.7-i2v
